# AI Tab MVP 规格

> 状态：A0、A1、A2、A2.5 已完成；A3 联调、真机验证与试用待确认。本文继续作为只读 AI MVP 的范围与验收基线，不授权写入能力。

## 1. 目标

在微信小程序新增第四个原生 Tab「AI」。用户通过自然语言查询当前农场的数据；AI 只读取已经有权限访问的内容，并以简洁、可核对的方式回答。

首个写入试点为“创建地块”，但不属于只读 MVP 的交付范围。只有只读版本通过验证后，才按本文第 10 节进入写入阶段。

## 2. 用户与上下文

- AI 仅服务已登录用户。
- 一次对话始终绑定一个农场和一个用户；切换当前农场时不混用窗口。用户可在“我的 → AI 对话”打开自己仍有成员权限的历史窗口。
- 当前农场由服务端 `GET /farms/current` 初始化。创建窗口时客户端仅提交当前农场 ID；后续对话轮次只提交 `conversationId`，查询范围固定为会话绑定农场。后端每次仍重新校验当前 JWT 用户的 `FarmMember` 身份，不信任客户端缓存。
- 所有农场默认开启 AI。Farm 的 OWNER 可关闭本农场的 AI；关闭后，该农场的所有成员均不能发送 AI 请求。OWNER 可重新开启；不做用户级白名单。
- 无当前农场时不能发送问题，页面提供进入“我的农场”的直接操作。

## 3. 只读 MVP 范围

### 3.1 支持的问题

- 当前农场、地块及地块详情查询。
- 当前或历史种养查询。
- 农事、收获和最近动态查询。
- 种类、农事类型等系统选项查询。

AI 可以为完成问题进行多次受控查询，例如先按名称查地块，再读取唯一匹配的地块详情。

### 3.2 对话体验

- 新增 `pages/ai/index` 原生 Tab 页面，使用普通 HTTP 请求返回完整回答；本 MVP 不做流式逐字输出。
- 用户可开启多个窗口；窗口与消息持久化到服务端，并按用户与农场私有隔离。模型每次只读取该窗口最近 8 轮，页面恢复历史时不重新发送完整历史给模型。
- AI Tab 顶部不放会话操作；输入栏在发送按钮旁提供无底色的“＋”新对话按钮。点击后清空当前活动窗口，首次发送时才创建新的服务端窗口；生成回复期间该按钮禁用。
- 初始对话在推荐问题上方显示低权重提示“目前仅支持查询 · 新建和记录请使用原有功能”；首条消息出现后隐藏。该提示只说明当前 MVP 边界，不提供 AI 写入入口。
- 会话管理入口位于“我的 → AI 对话”，用于查看、恢复或删除历史窗口；管理页没有窗口时可返回 AI Tab 开始新对话。
- 用户可查看和删除自己仍有成员权限的窗口；主动退出或被移出农场时，后端在成员关系变更事务中物理删除该用户在该农场的全部窗口和消息。
- 回答只使用纯文本、换行和简单列表。AI 输出不作为 HTML 或任意 Markdown 直接执行或渲染。
- 当名称匹配多个地块、种养或种类时，AI 必须展示候选项并要求用户明确选择，不得猜测。
- 回答中的业务对象可提供原生跳转入口；入口只能指向用户已有权限的既有详情页。

### 3.3 明确排除

- 所有写入、编辑、删除、结束种养、成员管理和登录相关操作。
- 收藏、分享和上传图片／语音。
- H5、`web-view`、流式输出、向量检索、RAG、通用 Agent 框架和模型直连。
- 模型自主调用任意 API、URL、数据库查询或后台任务。

## 4. 关键用户场景

### S1：查询当前种养

用户在当前农场问：“现在有哪些种养？”

AI 查询当前农场的种养摘要，按现有 Production 状态和排序口径回答，并可跳转到具体种养详情。

### S2：按地块查询

用户问：“1 号大棚种了什么？”

AI 查询当前农场内地块名称。只有一个匹配项时读取详情；多个匹配项时先列出候选项；没有匹配项时明确说明未找到。

### S3：查询最近生产活动

用户问：“最近做了什么农事？”

AI 使用当前农场的活动或农事记录数据回答，不编造记录、数量、人员或日期。

### S4：无当前农场

用户尚未创建或加入农场时进入 AI Tab。页面不请求模型、不伪造回答，只提供进入农场管理的操作。

## 5. 业务与安全不变量

- AI 没有独立身份；所有访问都以当前 JWT 用户身份执行。
- 工具只能调用显式白名单中的只读业务 Service，不能访问 ORM Session、任意 URL 或内部 HTTP API。
- 工具结果必须限制在当前农场；非成员访问与现有接口一致，不能借由 AI 识别资源是否存在。
- 后端仍是字段、权限和业务规则的唯一裁决者；模型不能决定权限，也不能绕过规则。
- 不向模型发送完整手机号、JWT、数据库连接信息、未加入农场的数据或未被当前问题需要的批量数据。
- 模型或上游服务错误仅返回统一的用户可理解失败提示，不回传密钥、调用栈或上游响应原文。

## 6. 数据告知与最小化

用户首次使用 AI 前，页面必须展示当前数据告知版本的页面内确认层。确认层不得依赖系统弹窗回调，避免在小程序运行环境中静默阻断发送。建议文案为：

> 使用 AI 时，你输入的问题，以及回答所需的当前农场业务数据会发送至 DeepSeek API 处理。请勿输入手机号、身份证等与农场管理无关的个人信息。

用户选择“暂不使用”时不发起模型请求；选择“同意并使用”后，客户端以当前用户和告知版本在本地记录确认状态。告知内容变更时提升版本号并再次展示。该确认是 demo 阶段的产品告知机制，不替代上线前应完成的隐私政策与合规评审。

发送范围遵循最小化原则：

- 始终可能发送用户问题及本轮必要的上下文。
- 工具只发送回答所需的农场业务字段，例如地块／种类名称、状态、日期和数量。
- 不发送 JWT、手机号、数据库密钥、完整 FarmMember 列表、无关农场数据或完整备注。
- 只有用户明确询问人员信息时，才发送回答所需的操作人展示名。
- 服务端保存用户问题和助手纯文本回答，以及已校验的对象引用／候选项；不保存 JWT、模型原始响应、完整工具结果或工具调用参数。

## 7. MVP 成功标准

- 用户可以从第四个原生 Tab 在当前农场完成 S1 至 S3。
- 每个回答均可追溯到实际工具结果；无法确定时会追问或说明无法查询。
- 非成员无法通过 AI 获得任意农场数据。
- 所有新建和已有农场默认可用；OWNER 关闭 AI 后，所有成员无法继续向该农场发起 AI 请求。
- 没有 AI 工具具备写入能力，数据库业务表在 AI 对话过程中不发生写入。
- 首次使用时，未确认数据告知的用户不会向 DeepSeek 发起请求。
- 页面满足既有 Token、页面层级、空状态和错误状态规范；不添加大面积说明性文本或与现有设计基线冲突的视觉样式。
- 后端测试、Ruff、前端 TypeScript 检查和微信小程序构建通过；至少在微信开发者工具及一台真机完成核心场景验证。

## 8. 待确认决策

这些决策在开始实现前必须确认，但不影响先评审本规格：

1. 已确认模型供应商为 DeepSeek 官方 API，模型为 `deepseek-v4-flash`；仍需确认 API 账号开通、可用地域与密钥在部署环境中的保管方式。
2. 已确认：AI 默认对所有农场开放；提供 OWNER 可控的农场级开关。
3. 已确认：用户首次使用前显示本规格第 6 节的数据告知；仅发送最小必要数据。
4. 已确认：每用户每天 20 次只读提问；单次问题最多 1,000 字；最近保留 8 轮上下文；超额后提示次日再试。

默认建议：后端集中配置 DeepSeek 官方 API；问题与最小化工具结果用于生成回答；所有农场默认可用，由 OWNER 按农场关闭；试用期使用已确认的单用户限额。

## 9. 非目标与后续边界

AI 不是农场数据的事实来源，也不替代现有表单。业务对象的详情、编辑和记录流程继续使用原页面。

当只读版本验证通过后，才评估下一个受控动作“创建地块”。其他写入能力需要独立规格，不因该试点自动获得授权。

## 10. 写入试点：创建地块（后续规格入口，暂不实现）

完整的安全边界、状态流转与后续确认项见《[AI 写入操作设计记录](./03-ai-write-action-design.md)》。本节仅保留产品范围约束。

创建地块需满足以下额外规则，未全部实现前不得开放：

- AI 只生成结构化草稿，必填字段为名称、类型、面积数值和面积单位；缺失时追问，不能自行补造。
- 页面使用原生确认卡完整展示草稿；只有 OWNER / ADMIN 明确确认后才执行。
- 后端生成一次性、短时效的待确认操作，确认接口使用幂等键；模型不能直接执行 `create_plot`。
- 确认时再次校验 JWT、FarmMember 角色和地块请求 Schema，并记录操作来源、确认人、最终参数与结果。
- 相关数据表必须通过新的 Alembic migration 创建，不能修改历史 migration。
